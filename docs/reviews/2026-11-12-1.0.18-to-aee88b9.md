## P1：优先修复

### R01 — 并发撤销使会话撤销水位倒退

- 位置：`packages/auth/src/services/token.service.ts:804–811`；引入 `c52e7b7`。
- 触发：多个实例撤销同一用户，较早的缓存写延迟至较晚的撤销之后完成。
- 问题：共享缓存执行普通 `get → Math.max → set`，没有原子单调性保障。旧水位能够覆盖新水位。
- 证据：三个真实 TokenService 实例共享合成可延迟 cache。A 计算 1 秒水位；C 签入 iat=2 秒的 token；B 在 3 秒撤销后 token 判定 `user_revoked`；释放 A 写入后同一 token 又通过。
- 影响：已经撤销的 token 可重新有效。合成 cache 证明调用顺序缺陷，尚未运行真实 Redis 并发测试。
- 修复：原子递增/原子取最大值或受事务保护的撤销版本；补跨实例乱序完成测试，不能只在单进程做 `Math.max`。

### R02 — 管理员修改邮箱提交后，失败的会话撤销无法重试

- 位置：`packages/admin/src/users/users.controller.ts:206–213`；`packages/back-office/src/accounts/admin-user-hooks.ts:22–28`。
- 触发：先提交敏感字段修改，随后执行撤销 hook；hook 遇到临时错误，再提交相同修改。
- 问题：第二次读到邮箱已经修改，`sensitive=[]`，因此成功返回却不再运行撤销 hook。与 `users.options.ts` 所述重试契约相反。
- 证据：第一次 hook 注入失败，第二次请求成功但 hook 总共只执行一次；修改前的 session 仍通过 `AccountService.currentUser()`。
- 影响：旧会话及凭据版本未按敏感修改要求失效。相关逻辑来自 `117ed9c` / `c52e7b7`，新 host 保留。
- 修复：修改与撤销放入同一事务，或持久化待执行撤销意图并确保幂等重试；测试“提交成功、后置 hook 失败、同请求重试”。

### R03 — 两笔叠加套餐全额退款后，仍保留付费权益

- 位置：`packages/payment/src/plans/subscription-assignment.ts:424,430–433`；引入 `305f24b`（1.0.21）。
- 触发：同套餐两笔 ONE_TIME 购买 A、B 叠加时长，先退最新 B，再退 A。
- 问题：B 退款缩短期限，却继续保留 `paymentReference=order:b`；A 退款因 `not_current` 被忽略。
- 证据：6 月 1 日开始两次 30 天购买，期限至 7 月 31 日；退 B 后至 7 月 1 日；退 A 返回 `not_current`，最终仍 ACTIVE 至 7 月 1 日。真实服务、合成 store 的定向断言失败。
- 影响：全部款项退回后仍有付费权益。已有 recurring 测试在两次退款中手动更换 paymentReference，掩盖了真实调用路径。
- 修复：持久记录每笔付款/退款贡献，按剩余未退款证据重算权益及当前引用；覆盖正序、逆序、三笔叠加和预付周期。

### R04 — 未支付 checkout 遮蔽有效订阅，允许再买一个仍会扣费的订阅

- 位置：`packages/back-office/src/subscriptions/billing-link.ts:24–35`；调用点 `packages/payment/src/plans/subscription-assignment.ts:315–318`。
- 触发：同一用户先打开两个 checkout，支付其中一个后，保留另一个未过期 pending checkout，同时已有有效 provider subscription。
- 问题：查询把 order 与 subscription `UNION ALL` 后直接 `LIMIT 1`，先返回 order；准入逻辑仅阻止 `kind=subscription`。
- 证据：实际 SQL 在内存 PGlite 返回 `{kind:'order'}`，传入实际 `admitPurchase()` 后不同套餐购买获准。真实 PostgreSQL 多连接行为未验证。
- 影响：旧订阅仍在扣费时可再创建新的扣费订阅；某些允许 order 的管理操作也可能跳过订阅限制。
- 版本：模板在 `0de37ac` 引入，`305f24b` 抽入 host。
- 修复：显式优先检查 provider subscription，或返回并同时检查两类阻塞条件；不要依赖 UNION 输出顺序承载业务优先级。

### R05 — AI 生成成功、完成事务失败，会再次调用计费生成接口

- 位置：`packages/ai-tasks/src/ai-task.service.ts:550–556,792–801`；引入 `a8ca9ef`（1.0.20）。
- 触发：同步生成已经成功，但写输出行/确认积分的最终事务暂时失败。
- 问题：未持久化可恢复的成功结果；durable retry 仍见 `providerTaskId=null`，重新执行生成。单次调用的 `maxAttempts:1` 不约束任务级重试。
- 证据：真实 AITaskService、DurableWorkerRuntime、PostgresTaskRepository 配合 PGlite；首次输出 INSERT 注入故障。第二次任务完成，同一任务 `generate` 次数为 2。
- 影响：重复供应商费用、重复产物；不是已证实的用户积分重复扣减。
- 修复：区分未提交、提交结果未知、结果已知待结算，持久化成功结果后独立重试结算；供应商支持时传幂等键。异步提交成功但 task ID 落库失败的相似窗口还需补测。

### R06 — 图片任务按 2–4 张收费，内置 OpenAI 实际只交付 1 张

- 位置：新计费调用 `templates/server/src/ai-tasks/ai-tasks.service.ts:121`；适配器 `packages/ai/src/providers/dalle.provider.ts:33–46`。
- 触发：内置 ai-openai 提供商，用户选择 count 大于 1。
- 问题：计费预留并确认 `unitPrice × count`；DALL-E 3 强制 n=1，DALL-E 2 虽发送 n=count 却仅返回 `response.data[0]`。
- 证据：模拟 SDK 分别请求两个模型且 count=4：实际 n 分别为 1、4，均只返回第一张。
- 版本：适配器原有行为早于范围；`a8ca9ef` 新增的计费任务把它变为本范围的交付/收费缺陷。
- 修复：按模型能力限制数量或完整保存全部响应图片；交付不足时不能确认全额费用。补模型能力—请求数量—实际产物—结算数量契约测试。

### R07 — AI 输出下载没有期限，可以长期占满 worker 并冻结积分

- 位置：`packages/ai-tasks/src/ai-task.service.ts:692–696`，期限检查 `:543`；引入 `a8ca9ef`。
- 触发：供应商结果 URL 连接或读取持续停滞。
- 问题：只传 worker abort signal，没有覆盖响应和流读取的下载期限；运行中不再检查 deadline。心跳持续续租，租约回收无法释放该任务。
- 证据：实际服务/PGlite，图片 maxWaitMs=50；模拟停滞下载，150ms 后期限已过但仍 PROCESSING/storing、signal 未中止，最后由测试主动 abort 清理。
- 影响：占用工作槽及积分冻结；默认两个并发槽时两个停滞任务即可阻塞后续任务。
- 修复：独立总期限和空闲期限，与 worker signal 合并；失败/取消后关闭源流并走明确的积分结算/释放流程。

### R08 — Redis 恢复后持续删除同键的新缓存

- 位置：`packages/cache/src/redis-cache.service.ts:228–237`；引入 `c52e7b7`。
- 触发：断连期间缓存 SET 进入 backlog，恢复时它已过期，之后业务向同键写入新值。
- 问题：回放对过期 SET 执行 DEL，但仅删除 `op==='del'` 的 backlog 项；过期 SET 留在 backlog，后续访问又删除新值。
- 证据：模拟 Redis 断连/恢复，`set('profile','fresh',60)` 成功后紧接 `get` 返回 null，底层新值被删除。
- 影响：缓存正确性破坏、反复回源，backlog 容量也被永久占用。
- 修复：按回放时捕获的条目身份移除已完成操作，保护期间新加入的操作；补“过期→恢复→同键重写”回归。

## P2：功能、恢复和交付问题

### R09 — Web 页头混用不同账户的身份和 token

位置：`templates/web/src/lib/site/session.ts:20–22`；新客户端引入 `5280170`。同浏览器标签 A 保留 Alice 状态，标签 B 登录 Bob 导致共享 Cookie 改变；A token 过期刷新得到 Bob token，仅更新 token，没有同步/校验 user 和 permissions。真实 shellClient/store 合成复现返回 Bob 余额，但 store 为 Alice 身份/Bob token，后续操作可能作用于错误账户。属于同浏览器多账户状态混淆，不是远程认证绕过。主 httpClient 的同类配置早于本范围，也应同步修复。复用已有 `createCookieSession` 身份校验和跨标签同步，补实际双标签用例。

### R10 — 缓存刷新接口先无界读取，再判断请求体大小

位置：`templates/web/src/app/api/revalidate/route.ts:18–24`；引入 `5280170`。启用 REVALIDATE_SECRET 后，无 Content-Length 的未签名流式请求绕过前置大小检查，`request.text()` 全部读完才返回 413。真实 POST handler 对 1 MiB 合成流读取了全部字节，尽管政策限制为 16 KiB。应按字节累计读取、超限立即 cancel，并提前拒绝缺失/明显非法认证头；不依赖客户端长度头。

### R11 — CRUD 事务传播遗漏动态查询

位置：`packages/crud/src/base.service.ts:117`、`packages/crud/src/dynamic-query.service.ts:432,574`；引入 `117ed9c`。CrudService 代理自身 db，但独立 DynamicQueryService 保留 root adapter。同一事务 create 后 findOne 能读到，findAll 却返回空；countByQuery、exists、动态分页同样受影响。真实服务/合成根与事务 adapter 已复现。将动态查询接入同一事务上下文，补读己之写与回滚可见性测试。

### R12 — 存活缓冲实例不回收后来崩溃的同伴工作

位置：`packages/buffer/src/persistence-buffer.ts:160–162`；引入 `c52e7b7`。`reclaimed` 使 `.processing` 回收每个实例仅执行一次；首次 flush 后同伴进程崩溃，文件持续滞留直到重启/创建新实例。实际临时文件系统复现：空 flush 后放入已不存在 PID 的认领文件，连续两次 flush 均未处理。应限频、周期性回收，保留活跃认领保护。

### R13 — revision=0 的支付订单会选择错误的 test/live 凭据

位置：`packages/back-office/src/billing/payment-credentials.ts:269–274`；模板引入 `1696a82`，`305f24b` 抽取。环境配置创建 `payment-stripe@0` 订单，随后同 account scope 保存 test→live 凭据；`minimum>0` 才检查原 mode，因此旧订单选择新 live adapter。合成 resolver 已复现，原 test 环境仍可用。影响为订单确认/恢复访问错误环境；未验证真实 Stripe，也不声称已经发生真实扣款。revision 0 同样需要固定原始 mode。

### R14 — 请求在异步获取 provider 之前断开，租约无法释放

位置：`packages/back-office/src/settings/hot-apply.ts:137–140`；引入 `1696a82`。close 监听在异步 slot 获取后注册；客户端此前已发出 close，回调仍调用 next 并永久等待另一个 close。实际 HotProvider 合成事件测试中 close 后 dispose 次数为 0，应为 1。配置热替换可能长期积留连接/客户端。提前追踪终止状态，拿到租约后发现已断开立即释放且不进入后续处理。

### R15 — 新邮箱登录模式无法登录后台创建的大写邮箱

位置：`packages/back-office/src/accounts/account.service.ts:409–413` 与 UsersController.create/update；引入邮箱登录 `aee88b9`。登录把邮箱小写化，后台写入不统一规范，精确查询找不到。实际控制器创建 `Alice@Example.invalid` 后，同邮箱正确密码仍返回 401。统一所有写入点/查询策略；修复前检查历史大小写碰撞，不能无检查批量 lower()。

### R16 — TOTP 的数据库认领失败仍消耗本地验证码

### R21 — 冷缓存下制品验收的 create 阶段无法获取 CLI

### R22 — 符号链接路径使检查脚本静默成功

位置：`scripts/prepare-skill-block-catalogue.mjs:248`；引入 `1696a82`。入口比较 resolve(argv[1]) 与 fileURLToPath(import.meta.url)，macOS `/var/...` 与 `/private/var/...` 不同，整个 CLI 被跳过。实际同一 stale 文件：逻辑路径返回 0 无输出，realpath 返回 1 并正确报过期；现有 drift.test 稳定失败。统一 realpath；acceptance/launch-ready、pack、file-registry 的同类入口一并核查。

### R23 — `create --no-web` 生成后无法通过自身 doctor

位置：`packages/cli/src/commands/create.ts:91–93`；doctor `:67–72`；引入 `5280170`。ACCOUNT_ORIGINS 按选中的应用生成，仅包含 admin:4201，却固定写 WEB_URL/SITE_URL 为 web:4202。实际 workspaceSettings/checkOrigins 合成测试产生两项错误。按所选应用生成配置，并让 doctor 明确理解无 Web 消费者。

## 改进顺序与回归范围

1. **先处理安全和资金不变量。** R01/R02 的撤销事务与原子水位；R03/R04 的付款证据、权益和订阅阻塞；R05/R06 的生成/交付/结算数量。用故障注入、乱序完成和多付款顺序测试，不能仅验证一次成功路径。
2. **完成超时与清理闭环。** R07/R14/R17 应覆盖等待响应、读取正文、客户端断开、provider 替换与应用关闭，检查最终 worker/积分/连接状态。
3. **把模板测试接入日常验证。** 根 Vitest 不发现 server 的 116 个测试文件；PR durable 任务仅覆盖指定少数库契约。增加无数据库模板测试、隔离 PG/Redis 集成任务和关键浏览器路径；本地源码验证与发布制品验证分开记录。
4. **减少测试与实现的脱节。** 子进程测试不能静默读取旧 dist；流程测试应覆盖真实组件/服务组合。尤其双标签换号、末页条目移除、完整退款、完成事务失败，不能只测试 reducer 或手工修正状态后的下一步。
5. **补公开 API 的类型级消费测试。** 运行时 Vitest 不会捕获 R20；使用小型 tsc 消费者验证自定义配置和浏览器/Node exports，真实制品兼容性留在发布阶段验证。
6. **明确缓存失效边界。** Web CDN 的 s-maxage/stale-while-revalidate 与 Next revalidateTag 是不同层；在有 CDN 的部署中单独验证发布/撤回的新鲜度。
