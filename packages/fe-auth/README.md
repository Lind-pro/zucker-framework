# Frontend authentication

`createAuthStore` provides typed Zustand authentication state, pluggable token/user storage, configurable persistence, permission matching and logout callbacks. The consumer owns its user shape, permissions, login routes, refresh-token policy and business cleanup.

`createUseAuthHydration(store)` binds a React hook to a store's optional Zustand `persist` API. It subscribes to completed hydration, returns `false` for server rendering or unavailable persistence, and disposes the subscription on unmount. This prevents applications from treating the first render before persistence is restored as an expired session.

`isSafeRelativeRedirect(value)` accepts only a local path beginning with `/`; it rejects schemes, protocol-relative paths, backslashes and CR/LF. Locale prefix removal, allowed destinations and fallback routes remain consumer policy. It expects the already-decoded query value used for navigation.

Session binding (`session.ts`) keeps a signed-in tab on one session. `jwtSessionKey(claims)` builds a comparison key from JWT claims the application chooses (for example `['sub', 'sid', 'cv']` for subject, persistent session id and credential version); the claim names stay consumer policy. `acceptsSessionToken(state, token, key)` allows a refreshed or header-supplied token only when it belongs to the current session, `sessionIdentity(state, key)` exposes the comparison value, and `createSessionRequestScope(read, subscribe, key)` returns an `AbortSignal` source that cancels in-flight requests when the user or session changes while surviving ordinary token rotation. Decoding a token only identifies a session for comparison; it never authorizes a request. Tests: `src/session.spec.ts`.

Cookie-refresh sessions (`cookie-session.ts`) are for apps whose access token lives in memory and whose refresh token is an HttpOnly cookie, with a token-free `{user, permissions}` summary persisted for reloads:

- `createSessionSummaryStorage({ key, storage? })` returns `{ storage, allowIdentityChange(), persistedIdentity() }`. Pass `storage` as `createAuthStore({ persistKey: key, persistOptions: { storage } })`. A write that would replace a summary another tab wrote for a different identity is skipped unless this tab just signed in (`allowIdentityChange`, called by the session on adoption), so a stale tab never overwrites another tab's account.
- `createCookieSession({ store, refresh, fetchAccount, toState, sessionKey, lockName = 'zucker-account-refresh', locks?, summary?, persistKey?, events?, statusOf?, subjectOf? })` returns `{ needsRestore, restore, settled, guardedRefresh, adoptToken, withLock, dispose }`. `restore()` runs once at a time per page under the `navigator.locks` lock (released when the exchange settles; the exchange carries its own timeout) and resolves `'authenticated' | 'anonymous' | 'failed'`; it never adopts a cookie that now belongs to another account than the persisted summary (signs out instead). 401/403 → `anonymous`; unknown outcomes (network, timeout, unload) → `failed` with the summary kept. `guardedRefresh()` is the refresh for `createHttpClient({ refreshWithCookie })`; it rejects with status 401 while the store is signed out (without calling `refresh`, also when the sign-out happens during the exchange), for tokens of another session, and — while only a summary without an access token is held — unless `subjectOf(token)` (default: the JWT `sub` claim; unidentifiable tokens are rejected) is the summary's user id. With `persistKey`, a `storage` event that shows another tab signed out or switched account signs this tab out locally (without touching that tab's summary).

`refresh` is typically `createRefreshExchange` + `createKeepaliveCookieRefresh` from `@zucker-framework/fe-http-client`; `@zucker-framework/fe-admin` composes both. Tests: `src/cookie-session.spec.ts`.

Sign-in identifier (`login-identifier.ts`): `loginIdentifierInput(identifier = 'username')` returns the request field (`username`, `email` or `login`), input `type`, `inputMode` and `autoComplete` (`username`, the login-form identifier token, also for addresses) for the account host's `login.identifier` option (`'username' | 'email' | 'username-or-email'`); `loginRequestBody(identifier, value, password)` builds the `POST /authorize/login` body with the identifier trimmed and the password as typed. Labels stay in the application's i18n. Tests: `src/login-identifier.spec.ts`.

The package keeps React and Zustand as peer dependencies and has no dependency on a product or backend package. New exports require validation and an immutable package release before published consumers can adopt them. Focused test sources are `src/hydration.spec.tsx`, `src/redirect.spec.ts` and the existing store tests.
