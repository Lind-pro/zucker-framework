# CLI audit and project tooling

The package root exports `auditModuleWiring`, `findTransactionBoundaryViolations`, `checkTransactionBoundaries`, `auditFrameworkSourceText` and `auditPnpmWorkflowVersions`. Importing that root loads only the library; it does not parse process arguments, read environment files, connect to services or execute CLI commands. The `zucker` executable keeps its existing `dist/index.js` path through a separate bin entry.

Module wiring checks use the TypeScript AST to identify Nest scheduler/cron imports, provider registrations, lifecycle declarations, guard composition and lifecycle aliases. Consumers supply their source root, scheduler owner, expected guards and infrastructure-provider owners. Transaction checks likewise receive root-client names and service/external-call patterns. Framework import checks accept consumer runtime-import restrictions; workflow checks receive the package-manager pin and workflow contents.

These are syntactic checks, retaining the original limits: they do not resolve a complete TypeScript program, infer dynamic module factories or prove database/provider behavior. Directory scanners read only the selected local source. Product module lists, service names, repository paths, workflow sets, command dispatch and output formatting stay in consumers.

TypeScript is a declared runtime dependency of these audit APIs. The release retains both CJS/ESM library entries and the executable. Source tests in `src/tooling/tooling.spec.ts` plus consumer characterization tests require validation before an immutable release. Merely importing the package is not authorization to run an audit or release command.

`@zucker-framework/cli/agent-instructions` is a separately exported, directly runnable JavaScript entry. Its `auditAgentInstructions(repository, policy)` checks canonical skill metadata, local Markdown links, configured compatibility aliases and optional Git-ignore visibility. Callers select document paths, alias locations/targets and whether reference-document aliases are permitted. The module imports only Node built-ins, has an explicit declaration file and does not load the TypeScript tooling entry or the CLI executable.

This exact `tooling/agent-instructions.mjs` file is included in the published package without a build transformation. Framework's own bootstrap script references that same in-repository module before dependency installation; external consumers use the published package subpath. There is no copied fallback implementation. CNIPA prepares its pinned root tooling dependency with a filtered frozen install and disabled lifecycle scripts; instruction validation still needs no application build, database or provider access.

## Local project initialization (not yet released)

The following behavior is implemented in the current local source; it is not a claim about an existing registry artifact or a version named in the source manifest. The established audit exports above and the new initialization behavior must be verified against the artifact a consumer actually installs.

`init --template admin`, `init --template web` and `init --template server-full` read `dist/project-templates.json`. They always use this CLI bundle, even when a Framework checkout is nearby. Missing or invalid bundled assets fail initialization instead of falling back to neighboring source. `scripts/prepare-cli-templates.mjs` prepares the Admin/Web/full Server assets and the consumer instruction text; `scripts/prepare-cli-catalog.mjs` records dependency versions and the runtime baseline. The CLI build prepares both files beside its executable.

The bundled assets include application source, local TypeScript/lint/style configuration, translations, README, `.env.example` and ignore rules. Collection excludes private environment files, known credential file extensions, symlinks, dependency/build/cache directories, generated Prisma clients and Next type files, and runtime uploads. Dependency entries using `workspace:*` are replaced from the catalog before normal consumer installation; catalog entries still require real matching artifacts. Existing target directories are rejected.

`server-full` is the deterministic complete Server entry. It always uses bundled assets from `templates/server`, including the Prisma schema, migration lock and migrations, Nest/Prisma/ESLint configuration, account composition and setup instructions. Required asset validation rejects a missing migration or entrypoint before writing a consumer. A new `server-full` target receives a `0600` private `.env` derived from the safe example with an independent random JWT secret; no source private environment is copied and no secret is printed. Configure the consumer's PostgreSQL, origins and SMTP, run `pnpm prisma:generate` and `pnpm db:migrate`, then use `pnpm dev`; schema push cannot replace the credential-version migration. Updated auth/admin contracts must be consumed from matching local fixed artifacts until their release is verified.

The existing `--template server` retains its prior behavior: copy the checkout's `templates/server` when present at its existing location, otherwise generate the independent minimal Server skeleton. It does not silently become `server-full`; its fallback remains an in-memory demonstration even if a `DATABASE_URL` is supplied without changing module composition. Neither initialization path proves all optional payment, storage or notification integrations are operational.

All initialization paths call the new local `installConsumerAgentInstructions(repository, source, options?)` export from `@zucker-framework/cli/agent-instructions`. It installs a consumer-owned `AGENTS.md` and attempts the relative `CLAUDE.md -> AGENTS.md` link; existing policies are preserved. Unsupported symlinks produce a warning while leaving AGENTS usable. The installer does not silently introduce a competing canonical file beside an existing noncanonical Claude-only policy. This installer addition also awaits a versioned release; do not assume older copies of the audit subpath export it.

Default local wiring is Server `4200` with `/api`, Admin `4201` with server-side `API_PROXY_TARGET=http://localhost:4200` preserving that prefix, and Web development `4202` with `API_URL=http://localhost:4200/api` as the full backend API base. Browser clients continue to call `/api`. Web production `start` retains Next's `PORT`/`3000` behavior. See the [consumer guide](../../docs/getting-started.md) for project setup and deployment boundaries.

`src/commands/init.spec.ts`, `tooling/agent-instructions.test.mjs` and the frontend `config.test.mjs` files cover the relevant local generation, preservation and configuration contracts. Separate artifact validation installed the local CLI tarball and generated a standalone Server with pnpm 11, local fixed auth/admin artifacts and exact versions of the remaining Framework dependencies. It passed independent lint, type checking and Nest compilation, both migration SQL files in an isolated PostgreSQL schema, explicit administrator setup, login, management authorization, persistent sessions across process restart, logout revocation and missing-mail failure behavior. The temporary schema and processes were removed. This proves that tested local artifact set, not a registry release, real SMTP delivery or all payment/storage/notification integrations; SQL replay does not claim a separate `prisma migrate deploy` acceptance.
